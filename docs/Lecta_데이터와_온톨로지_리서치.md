# 데이터 확보와 취향 온톨로지 리서치

세 가지 질문을 조사했습니다. 첫째는 TuneMyMusic처럼 플레이리스트를 불러올 수 있는지, 둘째는 영화, 음악, 책, 전시, 뮤지컬, 오페라, 콘서트 데이터를 어디서 확보하고 이미지 저작권을 어떻게 풀지, 셋째는 콘텐츠를 어떻게 분류할지(온톨로지)입니다. 셋째는 "나도 모르던 취향을 찾아 이름 붙여 준다"는 목표에 맞춰 설계했습니다. API 조건은 2026년 11월에 공개 문서로 확인한 내용이라 실제 연동 전에 약관을 다시 확인해야 합니다. 저작권 부분은 법률 자문이 아니라 위험을 줄이는 실무 방법입니다.

---

## 1. 플레이리스트 불러오기

### TuneMyMusic은 어떻게 동작하나

TuneMyMusic은 Spotify, Apple Music, YouTube Music, Deezer, TIDAL 같은 서비스의 **공식 API**에 사용자가 로그인해 권한을 주면 플레이리스트를 읽고 옮기는 방식입니다. 공식 API가 없는 곳은 자유 텍스트 입력, 파일 업로드, 플레이리스트 URL 붙여넣기로 받습니다. 멜론, 지니, 벅스는 지원 목록에 없고, 개발자용 공개 API나 임베드 위젯도 제공하지 않습니다. 그래서 **TuneMyMusic을 Lecta에 붙이는 것은 불가능하고, 같은 방식을 직접 구현해야 합니다.**

### 플랫폼별 가능성

| 플랫폼 | 방법 | 조건과 한계 | Lecta에서 |
| --- | --- | --- | --- |
| YouTube, YouTube Music | 공개 플레이리스트 URL을 붙여넣으면 YouTube Data API로 곡 목록 읽기 | 기본 할당량 하루 10,000단위, 목록 조회 한 번에 1단위. 공개 목록은 API 키만으로 읽을 수 있는 것으로 안내됨 | **가장 쉬움. 이번 학기 1순위** |
| Spotify | 사용자 로그인(OAuth) 후 플레이리스트 읽기 | 2025년부터 확장 접근은 월 사용자 25만 명 이상 법인만. 개발 모드는 등록한 사용자 25명까지 | 수업 시연용으로는 가능(팀원과 테스터를 등록) |
| Apple Music | MusicKit으로 사용자 라이브러리의 플레이리스트 읽기 | 개발자 토큰 발급에 Apple Developer Program 가입(유료)이 필요하고, 사용자 토큰도 필요 | 비용 때문에 후순위 |
| 멜론, 지니, 벅스, FLO | 공개 API 없음 | 플레이리스트 화면의 곡 목록을 복사해 붙여넣거나 스크린샷을 올리면, LLM이 "곡명과 아티스트"로 정리하고 MusicBrainz나 iTunes 검색으로 짝을 맞춤 | **텍스트와 스크린샷 붙여넣기로 지원** |
| 공연 관람 기록(인터파크, 멜론티켓) | 공개 API 없음 | 티켓 사진을 올리면 LLM이 공연명, 날짜, 장소를 읽고 KOPIS에서 공연을 찾아 연결 | 데모데이 후보 |

### 제안: "링크나 목록을 붙여넣으면 내 방이 된다"

1. 사용자가 YouTube 플레이리스트 링크, Spotify 링크, 또는 멜론에서 복사한 곡 목록을 붙여넣습니다.
2. 링크는 해당 API로, 텍스트와 스크린샷은 LLM으로 곡명과 아티스트를 뽑습니다.
3. 뽑은 곡을 MusicBrainz나 iTunes 검색으로 정규화해 곡 단위 작품으로 만듭니다. 현장 피드백의 "곡 단위 추가"가 함께 해결됩니다.
4. 불러온 곡들로 바로 취향 분석(3장)을 돌려 "이 플레이리스트에서 찾은 당신의 취향"을 보여주고, 방 하나로 만들지 묻습니다.

이 흐름은 MCP 도구 `import_playlist`로도 열 수 있어서, 사용자가 쓰는 AI에게 "이 플레이리스트로 Lecta 방 만들어 줘"라고 시키는 장면이 됩니다.

| --- | --- | --- | --- | --- |
| 영화, 시리즈 | TMDB | KMDb(한국영상자료원), KOBIS(영화진흥위원회) | TMDB 포스터 | 비상업은 무료지만 출처, 로고, 보증 아님 문구 필요. 수익화 시 상업 라이선스 |

| 콘서트(대중음악) | KOPIS | Ticketmaster Discovery API(해외), setlist.fm(곡 목록) | KOPIS, Ticketmaster 이미지 | Ticketmaster는 하루 5,000회, 초당 5회 기본 할당. 한국 공연 범위는 확인 필요. setlist.fm은 비상업 무료 |

### 2.2 이미지 저작권을 줄이는 방법

같은 장면에서 쓸 수 있는 방법을 위험이 낮은 순서로 정리했습니다.

| 방법 | 설명 | 쓰는 곳 |
| --- | --- | --- |
| 1. 공식 임베드 | Spotify, YouTube, Apple Music이 제공하는 공식 플레이어 임베드는 플랫폼이 허용한 방식이라 앨범 아트가 그 안에 보여도 문제가 적음 | 곡과 앨범 상세 |
| 2. 이미지 사용을 허락하는 API의 이미지 | TMDB, 알라딘, Cover Art Archive, KOPIS처럼 API가 이미지 URL을 주는 곳의 주소를 그대로 표시하고 출처를 답니다. 파일을 우리 서버에 복제해 재배포하지 않습니다 | 작품 카드, 전시실 |
| 3. 링크와 함께 작게 | 이미지를 클릭하면 원 출처(구매나 상세 페이지)로 가게 하고, 썸네일 크기로만 씀 | 검색 결과 |
| 4. 사용자가 찍은 사진 | 책 실물, 티켓, 전시장 사진을 커버로. 저작권 문제가 없고 개인적인 기록의 느낌이 강해짐 | 공연, 전시, 내 방 |
| 5. 이미지 없는 커버 | 포스터에서 대표 색만 뽑아 색 블록과 글자로 만든 커버. 지금의 글자 표지를 발전시킨 것. 색 자체는 저작물이 아님 | 이미지가 없거나 조건이 불분명할 때 |
| 피할 것 | 검색 결과 이미지를 긁어 저장, 위키백과의 비자유 이미지를 계속 사용, 공유 카드에 포스터를 크게 넣어 외부로 배포 | |

공유 카드(SNS용 이미지)는 밖으로 나가 퍼지기 때문에 위험이 가장 큽니다. 공유 카드에는 5번(색과 글자)이나 4번(사용자 사진)을 기본으로 쓰고, 포스터는 작게 넣거나 링크로만 연결하는 것을 권합니다.

## 3. 취향 온톨로지

### 3.1 다른 서비스는 어떻게 분류하나

| 서비스 | 방식 | 누가 붙이나 | 배울 점 |
| --- | --- | --- | --- |
| **Netflix 마이크로 장르** | 76,897개의 세부 장르. 기본 장르(예: 드라마)를 중심에 두고, 배우, 감독, 시대, 장소, 형용사를 붙여 "Mad Libs"처럼 이름을 조합. 충분한 작품이 모이는 조합만 씀 | 사람(작가 지망생 태거)이 로맨스, 잔혹함, 기발함, 결말 같은 속성을 점수로 매김 | 작은 속성 집합을 **조합해 이름을 만드는 문법**. "Romantic"이 가장 많이 쓰인 형용사(5,272개) |
| **Pandora Music Genome Project** | 곡마다 약 450개 속성 중 장르별로 150~450개를 0~5점으로 평가(보컬 성별, 그루브, 기타 디스토션 등) | 음악가 분석가가 곡당 20~30분, 10%는 교차 검증 | 속성을 장르마다 다르게 두는 것. 사람이 붙이면 정확하지만 비쌈 |
| **Spotify 마이크로 장르와 Daylist** | 청취 데이터로 만든 수천 개의 세부 장르. Daylist는 시간대와 자주 듣는 장르로 "Boogie Post-Punk Revival Wednesday Afternoon" 같은 이름을 붙인 플레이리스트를 만들어 주고, 이 이름이 밈처럼 공유됨 | 행동 데이터와 알고리즘 | **이름 붙여 주기 자체가 공유 동기**가 됨. Lecta 목표와 가장 가까운 사례 |
| **Letterboxd 나노 장르** | 리뷰 같은 관객 반응 텍스트를 분석해 반응이 비슷한 작품끼리 묶고 "Suspense, Slick, Stylish"처럼 키워드 세 개로 이름 붙임. Nanocrowd와 협업(2022) | 사람들의 리뷰를 알고리즘이 묶음 | **감상 텍스트로 분류**하는 방식. Lecta의 "이유"와 같은 재료 |
| **StoryGraph** | 책마다 분위기(어두운, 감정적인, 모험적인 등), 속도, 인물 중심인지 이야기 중심인지를 독자들이 리뷰에서 고르고, 비율로 보여줌 | 독자 투표 | **같은 작품을 사람마다 다르게 느낀다**는 것을 비율로 표현 |
| **KOPIS 공연 장르** | 연극, 뮤지컬, 넌버벌, 클래식(기악, 성악, 오페라), 국악, 무용, 복합 | 공공 분류 | 공연 매체의 장르 축은 이 분류를 그대로 가져오면 됨 |

### 3.2 제안: 다섯 층의 온톨로지

키워드가 너무 많아지는 문제는 **층을 나누고, 사람이 관리하는 단어는 가운데 층에만 두는 것**으로 풉니다. 가장 추상적인 이름은 단어 목록이 아니라 분석 결과로 만들어 냅니다.

| 층 | 무엇 | 예시 | 누가 만드나 | 개수 |
| --- | --- | --- | --- | --- |
| 0. 매체 | 작품의 종류 | 영화, 시리즈, 책, 앨범, 곡, 전시, 뮤지컬, 오페라, 콘서트 | 고정 | 9개 안팎 |
| 1. 장르 | 매체마다 다른 장르. 매체를 넘는 장르군으로 묶어 연결 | 영화의 멜로와 책의 연애소설은 장르군 "사랑 이야기"로 연결. 공연은 KOPIS 분류 | 소스 메타데이터에서 자동, 장르군 매핑은 팀이 관리 | 매체별 장르 수십 개, 장르군 12개 안팎 |
| 2. 공용 감각 축 | 매체와 상관없이 쓰는 Lecta의 단어. 여섯 축으로 묶음 | 주제(상실, 성장, 고독), 정서(쓸쓸함, 설렘), 분위기(몽환적인, 따뜻한), 형식(느린 서사, 회고하는 화자), 감각(여백이 많은, 소리의 질감), 밀도(가벼운, 묵직한) | 팀이 관리하는 통제 어휘. 지금 태그 39개를 이 여섯 축으로 재배치 | 축마다 8~12개, 전체 50~60개 |
| 3. 개인의 해석 | 같은 작품을 사람마다 다르게 느낀 것. 작품의 속성이 아니라 "사람, 작품, 단어, 근거 문장"의 관계로 저장 | A는 Before Sunset에서 "설렘", B는 "쓸쓸함"을 느낌. 사람들의 해석을 모으면 "이 작품을 쓸쓸하다고 느낀 사람 62%" | 사용자가 쓴 이유를 LLM이 2층 단어로 연결하고, 근거 문장을 남김 | 사람마다 쌓임 |
| 4. 취향 이름 | 한 사람의 작품과 이유를 묶어 찾아낸 숨은 공통점에 붙인 이름 | "말하지 못한 사랑의 느린 이야기", "여름이 끝나는 자리의 쓸쓸함" | 분석과 LLM이 만들고 사용자가 맞다, 아니다로 다듬음 | 사람마다 3~6개 |

**추상성의 층위**는 이렇게 정합니다.
- 구체(소재, 배경, 장르)는 0층과 1층, 소스에서 자동으로 받습니다.
- 감정과 분위기 같은 중간 추상은 2층, 통제 어휘로 관리합니다. 키워드가 늘어나는 것을 막는 지점이 여기입니다.
- 절제, 여운, 이방인의 시선 같은 높은 추상은 단어 목록에 넣지 않고 4층에서 이름으로 생성합니다. 그래서 단어 목록은 작게 유지되면서도 결과는 섬세해집니다.

### 3.3 태그는 어떻게 붙이나 (데이터가 없을 때부터)

| 단계 | 방법 | 비고 |
| --- | --- | --- |
| 작품이 들어올 때 | 소스의 장르를 1층으로 받고, LLM이 줄거리와 소개를 읽어 2층 단어를 신뢰도와 함께 제안(`LLM_SUGGESTED`) | Netflix와 Pandora는 사람이 붙였지만, Lecta는 LLM을 첫 태거로 씀 |
| 사용자가 이유를 쓸 때 | LLM이 이유 문장을 2층 단어로 연결하고 근거 문장을 저장. 이유 입력 칸 아래 감각 축 칩을 보여줘 고를 수도 있게 | 데이터가 처음부터 구조를 갖게 됨 |
| 검색할 때 | 칩으로 거르기(매체, 장르군, 감각 축)와 문장 검색("비 오는 날 혼자 보는 느낌")을 함께. 문장 검색은 작품 설명과 사람들의 이유를 임베딩해 비교 | 지금의 TF-IDF를 임베딩으로 확장 |
| 사람이 쌓이면 | 2층 단어별 투표 비율(StoryGraph 방식), 사용자들이 자주 쓰는 새 표현을 검토해 2층에 추가 | 감상 데이터가 쌓일수록 정확해짐 |

### 3.4 "나도 모르던 취향을 찾아 이름 붙여 주기"

| 단계 | 하는 일 | 사용자에게 보이는 것 |
| --- | --- | --- |
| 1. 모으기 | 담은 작품, 쓴 이유, 불러온 플레이리스트 | |
| 2. 두드러진 축 찾기 | 내가 고른 작품들의 2층 단어 비율을 전체 사용자 평균과 비교해 나에게 특히 높은 축을 찾음 | "다른 사람보다 '회고하는 화자'가 3배 많아요" |
| 3. 묶기 | 매체를 넘어 작품과 이유를 임베딩 공간에서 묶음(영화, 책, 곡이 한 묶음에 들어갈 수 있음) | 묶음별 작품 3~5개 |
| 4. 이름 붙이기 | 묶음마다 두드러진 단어와 공통된 이유 표현을 근거로 LLM이 2~5단어 이름을 만듦. 근거 작품과 근거 문장이 없으면 이름을 만들지 않음 | "말하지 못한 사랑의 느린 이야기" 와 근거 |
| 5. 말하지 않은 이유 찾기 | 작품들에는 공통으로 있는데 사용자가 이유로 한 번도 쓰지 않은 단어를 짚어 줌 | "직접 쓰신 적은 없지만, 좋아한 작품 다섯 개 모두 끝에서 과거를 돌아봐요" |
| 6. 다듬기 | 사용자가 맞아요, 아니에요를 고르면 다음 분석에 반영 | 취향 카드로 저장하고 공유 |

5단계가 "그냥 좋다고만 생각했던 것의 이유를 찾아 준다"에 해당합니다. Netflix가 속성을 조합해 장르 이름을 만들었다면, Lecta는 한 사람의 이유를 조합해 그 사람만의 취향 이름을 만드는 셈입니다. Spotify Daylist처럼 그 이름 자체가 공유하고 싶은 결과물이 되고, 앞서 논의한 "나를 드러내는 취향 페이지"의 핵심 콘텐츠가 됩니다.

### 3.5 감상 데이터가 쌓이면 해결될까

일부는 맞습니다. 사람이 많아지면 같은 작품에 대한 해석 비율(3층)과 비슷한 사람끼리의 추천이 정확해집니다. 하지만 두 가지는 처음부터 설계해야 합니다.
- **데이터의 모양:** 이유를 자유 글로만 받으면 나중에 쓰기 어렵습니다. 처음부터 2층 단어와 연결해 두어야 쌓이는 데이터가 분석 가능한 데이터가 됩니다.
- **혼자일 때의 가치:** 취향 이름은 다른 사람의 데이터가 없어도 내 작품과 이유만으로 만들 수 있습니다. 그래서 사용자가 적은 초기에도 "발굴" 경험을 줄 수 있습니다.
